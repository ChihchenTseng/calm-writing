## 1. 文件權威與變更規則

本文件是產品目的、研究邊界、輸出語言、資料與模型驗證要求的最高產品定義。若 README、舊版專案說明、程式註解或歷史實作與本文件衝突，以本文件為準，並建立工單處理差異；不得以修改程式的方式暗中改變本文件的產品邊界。

任何涉及健康宣稱、研究倫理、個資用途、正式產品輸入或低／中／高分類定義的變更，必須由 PM 建立可追溯工單，附上依據與風險，並依治理規則判斷是否需要產品負責人決策。

## 2. 產品定位

「寫字靜心」透過手寫過程特徵，提供當下壓力狀態的自我覺察提醒。產品的目的不是診斷疾病，也不得宣稱可取代醫師、心理師、量表或其他專業評估。

正式產品應：

1. 以低／中／高三段呈現狀態提醒；資料不足時明確顯示「資料不足」，不得勉強分類。
2. 使用溫和、非污名、非醫療診斷的文字，並提供適度休息、呼吸或尋求專業協助等一般性建議。
3. 清楚說明結果是根據手寫特徵推估，具有不確定性。
4. 不得要求使用者輸入 VAS、PSS-10 或其他主觀壓力自評作為正式產品推論輸入。

## 3. 使用者與研究對象

### 3.1 產品主要使用者

主要設計對象是中高齡使用者，以及關心自身身心健康與壓力狀態的人。介面應採易讀字級、足夠對比、清楚步驟、寬裕點擊區與不依賴專業術語的文字。

### 3.2 研究招募

研究資料蒐集目前不設定年齡限制。產品主要使用者與研究招募範圍是兩個不同概念，不得將「中高齡為主要使用者」誤寫成研究排除條件。

## 4. 現況與已知限制

1. 目前資料為 54 位獨立參與者，每人一次紀錄。
2. 現有資料沒有可供縱向追蹤的匿名 follow-up ID，因此不得將其描述成同一人的長期變化資料。
3. VAS 與 PSS-10 僅可作為研究訓練、標記、校準或驗證資料，不是正式產品推論時的必要輸入。
4. 現有資料以中間壓力區間居多，低與高區間樣本不足；任何整體準確率都可能掩蓋類別不平衡。
5. 歷史 `StressEngine` 為規則式原型，未完成足以支持正式效能宣稱的獨立驗證，不得稱為已驗證模型。

## 5. 手寫資料與必要特徵

### 5.1 原始事件最低要求

研究模式應保存足以重算特徵的去識別化筆畫事件：單調遞增時間、座標、有效壓力、pointer 狀態、筆畫起訖、畫布與裝置資訊。每筆輸出必須包含 `feature_schema_version`、程式 commit、瀏覽器／裝置類型、作業版本與缺值／fallback 標記。不得用靜默預設值偽裝成實測值。

### 5.2 新增 96 位參與者前的阻擋條件

在新增 96 位參與者、使總樣本目標達 150 人以前，必須先修正並以測試資料驗證下列特徵：

1. 暫停時間：定義筆畫內速度低於門檻或事件間隔超過門檻的計算方式，門檻與版本須隨資料保存。
2. 長暫停：門檻可設定；若沿用歷史值，預設為 2,000 ms，且必須記錄實際門檻。
3. 字距：以可重現的字元區段或格位計算；不得把負值直接截為零。間距與重疊應分開保存並檢查異常。
4. 速度變異：於固定單位、重採樣及平滑規則後計算標準差與變異係數。
5. 加速度與 jerk：從同一套重採樣／平滑後的速度序列計算，記錄單位與參數，避免噪音被放大。
6. 壓力變異：只使用有效筆落樣本，至少保存標準差、變異係數、有效樣本數與裝置支援狀態。
7. 抬筆時間：從一次 pointer-up 到下一次 pointer-down 計算，至少保存總和、平均、中位數、最大值、次數與作業時間占比。

PM 與 QA 必須在蒐集開始前確認定義、邊界案例、單位、測試治具及舊資料相容策略。若特徵定義變更，資料不得在沒有版本欄位的情況下混合。

## 6. 研究模式與正式產品分離

研究模式可以蒐集 VAS、PSS-10 與必要研究欄位，但必須清楚標示研究用途、同意內容、保存範圍與退出方式。正式產品的壓力提示流程不得要求上述量表作為推論前提。

研究資料匯出應符合：

- 不包含姓名、電子郵件或可直接識別個人的資訊。
- 欄位、單位、缺值語意與 schema 版本可追溯。
- 若未來需要追蹤，另行設計不可逆、可撤回且經審查的匿名識別方式；不得事後猜測參與者身分。

## 7. 模型、回測與驗收

### 7.1 分割與訓練

1. 資料切分必須以參與者為單位，避免同一人的資料同時出現在訓練與測試集合。
2. 採分層交叉驗證；重採樣、特徵選擇、標準化與類別權重計算只能在各訓練 fold 內進行。
3. 類別不平衡應使用類別權重、訓練 fold 內重採樣或其他可說明的方法處理，並與簡單 baseline 比較。
4. 每次回測保存 dataset hash、feature schema 版本、程式 commit、分割 seed、參數與執行時間。

### 7.2 必報指標

不得只報整體 accuracy。至少提供：

- balanced accuracy 與 macro F1；
- 低／中／高各類 precision、recall、F1 與樣本數；
- confusion matrix；
- 與多數類別及既有規則式原型的比較；
- 若輸出信心程度，提供校準結果或明確說明該數值不是機率。

正式模型與分類界線必須經獨立測試集合或預先定義的交叉驗證方案通過。若資料不足以支持三分類，系統應維持研究狀態並呈現資料不足，不得降低標準後宣稱完成。

## 8. 正式輸出要求

每次結果至少包含：

1. 狀態：低、中、高或資料不足。
2. 簡短且非診斷性的說明。
3. 不確定性或資料品質提示。
4. 一個可立即執行的溫和建議。
5. 當結果持續令人困擾時，建議諮詢合格專業人員的提示。

禁止使用「確診」、「罹患」、「醫療級準確」、「保證」等未被證據支持的文字。

## 9. 隱私、安全與可近用性

- 預設最小化蒐集；正式產品不得因分析而保存不必要的原始手寫內容。
- 任何網路傳輸、雲端保存或第三方服務都必須在實作前建立隱私與安全工單。
- 不在程式、紀錄、工單或 PR 中放置密鑰與個資。
- 鍵盤操作、焦點、顏色對比、錯誤提示及行動裝置觸控需納入 QA。

## 10. 發布與 Git 規則

1. `main` 代表可部署、已通過檢查的穩定狀態；不得直接推送功能程式。
2. 每個變更由工單建立功能分支與 PR，PR 必須附驗收條件、測試證據、風險及必要資料來源。
3. 只有一批達到可使用里程碑的功能才建立產品版本與 Git tag；每個小修正不自動增加公開版本號。
4. 公開 release note 只描述使用者可感知的新增、調整、修正及已知限制，不描述使用了哪一種 AI 或代理角色。
5. AI 協作方式可放在獨立治理文件，但不得污染產品介面與公開版本摘要。

## 11. 近期里程碑

### 兩週 MVP

- 完成第 5.2 節特徵定義與可重現測試。
- 建立研究資料 schema、缺值規則與版本欄位。
- 建立 PR 自動檢查及穩定的正式／研究入口。

### 一個月校準

- 完成具參與者隔離的 baseline 與回測流程。
- 針對低／中／高不平衡提出採樣與模型方案。
- 產出可重現報告並由 QA 驗證。

### 正式三分類前

- 補足資料並完成預先定義的驗證。
- 通過非診斷文字、隱私、可近用性與回歸測試。
- 由 PM 建立版本工單，QA 確認後才能發布。

## 12. 非目標

- 不提供疾病或心理健康診斷。
- 不以單次手寫結果取代專業評估。
- 不把未驗證規則引擎包裝成正式 AI 模型。
- 不以 VAS 或 PSS-10 作為正式產品使用者必填輸入。
- 不在特徵修正與資料版本完成前擴大蒐集 96 人。
